## 0. Резюме и главный риск

Задача `C = A + B` / `D = A - B` имеет арифметическую интенсивность
**AI ≈ 1 FLOP на 12–16 байт трафика** — это **memory-bound** ядро.
Roofline даёт: на больших `N` прирост от векторизации сам по себе ≈ 0,
всё упирается в пропускную способность DRAM.

Поэтому ТЗ строится так, чтобы отчёт был содержательным, а не «ускорения нет»:

1. Замеры делаются **свипом по размеру** `N` — так, чтобы рабочий набор попадал
   в L1, в L2 и в DRAM. В in-cache режиме векторизация даёт честные 4–8x,
   в DRAM-режиме — выходит на плато. Это и есть основной результат работы.
2. Отдельным этапом оптимизируется **трафик памяти**, а не арифметика:
   non-temporal stores (обход write-allocate / RFO), программный prefetch,
   слияние операций `+` и `-` в один проход.
3. Теоретический предел считается по **двум** моделям: по пиковой FLOPS
   (для in-cache) и по пиковой ПСП (для DRAM) — сравнение с ними обязательно
   по заданию («сравнение с теоретическими результатами»).

**Критерий успеха всей работы:** на каждом этапе E0→E4 показано измеримое
уменьшение времени (или объяснено, почему оно уперлось в теоретический предел),
и построена таблица «этап → время → speedup → % от предела».

## 1. Постановка задачи (раздел отчёта, обязательный)

### 1.1 Формальная постановка
Даны плотные матрицы `A, B ∈ R^{N×N}`, хранимые построчно (row-major),
элементы типа `float` (IEEE-754 binary32). Требуется вычислить:

```
C[i][j] = A[i][j] + B[i][j]
D[i][j] = A[i][j] - B[i][j]      для всех 0 ≤ i, j < N
```

Объём вычислений: `N²` FLOP на одну операцию, `2N²` на обе.
Объём данных: `3 · N² · 4` байт (или `4 · N² · 4` при вычислении обеих матриц).

### 1.2 Что нужно сделать
Оптимизировать программу и сравнить время работы вариантов:
- E0 — исходная программа без оптимизации;
- E1 — исходная программа, оптимизированная **только ключами компилятора**;
- E2 — **полуавтоматическая** векторизация (директивы + ключи + мелкая правка кода);
- E3 — **ручная** векторизация через NEON intrinsics;
- E4 — ручная оптимизация трафика памяти (non-temporal store, prefetch, слияние).

### 1.3 Подзадачи

- [ ] 1.3.2 Зафиксировать набор размеров `N` для свипа (см. §5.2).
- [ ] 1.3.3 Зафиксировать формат вывода замеров (CSV) — см. §6.4.

## 4. Этапы оптимизации (ядро работы)

Общее правило из задания: **на каждом этапе проверить, что время уменьшилось.**
Если не уменьшилось — этап не выбрасывается, а описывается с объяснением
(это тоже результат, особенно для memory-bound задачи).

### E0 — базовая версия, без оптимизации

- [ ] E0.1 Наивная реализация двойным циклом по `i`, `j` с двумерной индексацией
      `a[i*n + j]`, без `restrict`, без выравнивания.
- [ ] E0.2 Флаги: `-O0 -fno-vectorize -fno-slp-vectorize -fno-unroll-loops`.
      Дополнительно собрать вариант `-O1 -fno-vectorize` как «честный ноль»
      (на `-O0` clang не убирает даже лишние load/store, и baseline выходит
      неправдоподобно медленным → speedup раздувается). **В таблице показать оба**
      и явно оговорить, какой берётся за 1.0x.
- [ ] E0.3 Зафиксировать эталонный результат: сохранить `C` и `D` в память,
      посчитать контрольную сумму (FNV-1a по байтам) для §7.

**Ожидание:** ~1 элемент за несколько тактов, скалярные `ldr s0 / fadd s0 / str s0`.

### E1 — оптимизация только ключами компилятора

- [ ] E1.1 Тот же исходник `kernel_e0.c`, флаги:
      `-O3 -mcpu=<native|apple-m4> -funroll-loops`.
- [ ] E1.2 Дополнительно собрать и замерить варианты:
      `-O2`, `-O3`, `-Ofast`, `-O3 -ffast-math`.
      **Важно:** для поэлементного `+`/`-` `-ffast-math` не должен менять результат
      (нет редукции → нет переассоциации). Проверить это побитово (§7) и
      написать в отчёте — это хороший показатель понимания.
- [ ] E1.3 Выбрать ключи, дающие минимальное время (требование задания:
      «использовать ключи оптимизации, дающие наименьшее время»).
      Все замеренные комбинации — в таблицу, не только победитель.
- [ ] E1.4 Снять отчёт векторизатора:
      `-Rpass=loop-vectorize -Rpass-missed=loop-vectorize -Rpass-analysis=loop-vectorize`
      и `-fsave-optimization-record` → `results/opt-records/e1.opt.yaml`.
      Зафиксировать: **векторизовал ли компилятор сам**, и если нет — причину
      (обычно `cannot identify array bounds` / возможный aliasing `c` с `a`,`b`).

**Ожидание:** clang на `-O3` векторизует этот цикл автоматически, но вставит
**runtime-проверку перекрытия указателей** (memcheck) и скалярный хвост.
Именно это и снимается на E2.

### E2 — полуавтоматическая векторизация (директивы + мелкая правка)

- [ ] E2.1 Добавить `RESTRICT` ко всем трём указателям → убирает runtime memcheck.
      Проверить по opt-record, что проверка исчезла.
- [ ] E2.2 Свести двойной цикл к **одному линейному циклу** по `n*n`
      (матрица плотная и непрерывная → двумерный обход не нужен):
      `for (size_t k = 0; k < n*n; ++k) c[k] = a[k] + b[k];`
      Это убирает пересчёт `i*n` и упрощает векторизатору анализ.
- [ ] E2.3 Сообщить компилятору о выравнивании: `ASSUME_ALIGNED` на входе ядра.
      Цель — заменить невыровненные обращения на выровненные
      (требование задания: «обеспечить использование команд выровненного
      чтения и записи векторов»). На AArch64 проверять по исчезновению
      пролога-выравнивания и по использованию `ldp/stp q` пар.
- [ ] E2.4 Директивы:
      ```c
      #pragma clang loop vectorize(enable) vectorize_width(4) interleave_count(4)
      #pragma clang loop unroll_count(4)
      ```
      Замерить каждую комбинацию `vectorize_width × interleave_count`
      из {4} × {1,2,4,8} — выбрать лучшую, таблицу приложить.
- [ ] E2.5 Гарантировать, что `n*n` кратно 16 (или обработать хвост явно),
      чтобы не было скалярного эпилога на горячем пути.
- [ ] E2.6 Проверить, что время < E1. Если нет — разобрать по asm почему.

### E3 — ручная векторизация, NEON intrinsics

- [ ] E3.1 Реализовать ядро на `arm_neon.h`:
      ```c
      float32x4_t va = vld1q_f32(a + k);
      float32x4_t vb = vld1q_f32(b + k);
      vst1q_f32(c + k, vaddq_f32(va, vb));
      ```
      и `vsubq_f32` для вычитания.
- [ ] E3.2 **Развернуть цикл ×4** (16 элементов = 64 Б за итерацию) с
      независимыми регистрами — скрыть латентность load/store, дать
      планировщику выдать `ldp q0,q1` / `stp q0,q1` парами.
      Замерить развороты ×1, ×2, ×4, ×8 — таблица, выбрать лучший.
- [ ] E3.3 **Минимизировать обращения к памяти** (прямое требование задания):
      слить вычисление `C = A+B` и `D = A−B` в **один проход** — `A` и `B`
      читаются один раз вместо двух. Трафик падает с `(3+3)N²·4` до `(4)N²·4` байт,
      теоретический выигрыш **1.5×**. Это самый крупный честный выигрыш в задаче.
      Замерить отдельно: два прохода vs один слитый.
- [ ] E3.4 Проверить, что хвост (`n*n % 16`) обрабатывается скалярно и вне
      горячего цикла.
- [ ] E3.5 Проверить время < E2 и побитовое совпадение с эталоном.

### E4 — оптимизация трафика памяти

- [ ] E4.1 **Non-temporal store.** При обычной записи в `C` кэш делает
      write-allocate: строка `C` сначала **читается** из DRAM, хотя будет
      перезаписана целиком. Это лишние `N²·4` байт трафика (16 Б/элемент
      вместо 12). Обойти через `__builtin_nontemporal_store` (clang → `stnp`
      на AArch64). Ожидаемый теоретический выигрыш на DRAM-размерах: **+33%**.
      Проверить по asm, что действительно сгенерирован `stnp`.
- [ ] E4.2 **Программный prefetch** `__builtin_prefetch(a + k + DIST, 0, 0)`
      с подбором `DIST` ∈ {256, 512, 1024, 2048} элементов.
      На Apple Silicon аппаратный префетчер сильный — вероятно, выигрыша не будет;
      **отрицательный результат тоже фиксируется в таблице** с объяснением.
- [ ] E4.3 Проверить влияние выравнивания буферов на границу **страницы** (16 КБ
      на macOS/arm64) и разнесение `A`, `B`, `C` так, чтобы не возникало
      конфликтов по наборам кэша (cache set aliasing) при степенных `N`.
      Практика: аллоцировать с паддингом `+CACHELINE` и сдвигать базы.
- [ ] E4.4 Замерить и сравнить с roofline-пределом (§8). Довести до
      ≥70–80% от измеренной пиковой ПСП — это реалистичная цель.

### E5 (опционально, за рамками обязательной части)
- [ ] E5.1 Многопоточная версия (OpenMP / GCD / pthreads) — только если останется

- [ ] E5.2 Сравнение с `vDSP_vadd` из Accelerate как «промышленный baseline».

## 5. Параметры эксперимента

### 5.1 Тип данных
Основной — `float` (fp32, 4 лейна в NEON-регистре).
Опционально прогнать `double` (2 лейна) и показать, что speedup от векторизации
падает вдвое, а memory-bound-плато не меняется — сильный аргумент в выводах.

### 5.2 Свип по размеру (ключевой пункт ТЗ)

Подобрать `N` так, чтобы рабочий набор (`3·N²·4` байт) попадал в разные уровни:

| Режим | Рабочий набор | Примерные `N` (fp32, 3 матрицы) |
|---|---|---|
| в L1d (64 КБ) | < 64 КБ | 64, 72 |
| в L2 (4 МБ) | < 4 МБ | 256, 512 |
| за L2, в DRAM | >> 4 МБ | 1024, 2048, 4096, 8192 |

- [ ] 5.2.1 Пересчитать точные границы после уточнения размеров кэшей (2.2.1).
- [ ] 5.2.2 Для малых `N` время одного прохода наносекундное → гонять ядро
      в цикле `REPS` раз (подобрать `REPS` так, чтобы суммарное время ≥ 50 мс)
      и делить. Следить, чтобы компилятор не вынес вызов из цикла
      (`__asm__ volatile("" ::: "memory")` между повторами или `volatile` sink).
- [ ] 5.2.3 Для `N = 8192`: 3 матрицы × 268 МБ = 805 МБ — влезает в 16 ГБ, ок.
      Для слитого add+sub — 4 матрицы = 1.07 ГБ, тоже ок.

## 7. Контроль корректности

- [ ] 7.1 Эталон — результат E0 (скалярный, `-O0`).
- [ ] 7.2 Для `+`/`-` над fp32 **все варианты обязаны совпадать побитово**
      (одна операция на элемент, переассоциации нет). Сравнение — `memcmp`.
      Любое расхождение = баг, а не «погрешность fp». Это жёсткий критерий.
- [ ] 7.3 Контрольная сумма (FNV-1a по байтам результата) печатается каждым
      бинарём и сверяется скриптом.
- [ ] 7.4 Sink-переменная: после замера прочитать хотя бы один элемент `C`
      и учесть в контрольной сумме — защита от выбрасывания всего цикла
      оптимизатором (иначе на `-O3` можно «получить» время 0 нс).
- [ ] 7.5 Проверить граничные `N`, не кратные ширине вектора (например, 1023),
      — корректность хвоста.

## 8. Теоретический анализ (раздел отчёта, обязательный)

### 8.1 Модель roofline
- [ ] 8.1.1 Посчитать арифметическую интенсивность:
      - раздельные проходы, обычная запись: `1 FLOP / 16 Б = 0.0625 FLOP/Б`;
      - раздельные, NT-store: `1 / 12 = 0.083 FLOP/Б`;
      - слитый add+sub, NT-store: `2 FLOP / 16 Б = 0.125 FLOP/Б`.
- [ ] 8.1.2 Посчитать точку перегиба roofline:
      `AI_ridge = Peak_FLOPS / Peak_BW`. Для одного P-ядра M4 ориентировочно
      `Peak_FLOPS ≈ 4 лейна × 2 (FMA не применим, чистый FADD) × k портов × f`,
      `Peak_BW ≈ 120 ГБ/с`. Показать, что наши AI на 1–2 порядка левее перегиба
      → **задача жёстко memory-bound**.
- [ ] 8.1.3 Теоретический минимум времени для DRAM-размеров:
      `t_min = (bytes_per_elem · N²) / Peak_BW`.
      Пример для `N = 8192`, 16 Б/эл: `1.07 ГБ / 120 ГБ/с ≈ 8.9 мс`;
      с NT-store (12 Б/эл): `≈ 6.7 мс`.
      **Пересчитать по фактически измеренной ПСП (2.2.2), не по спецификации.**
- [ ] 8.1.4 Теоретический предел для **in-cache** режима — по ширине вектора:
      ожидаемый speedup E3/E0 ≈ 4× от SIMD плюс выигрыш от разворота.
      Именно здесь векторизация обязана быть видна.

### 8.2 Что сравнивать с чем
- [ ] 8.2.1 Таблица «этап → измеренное время → % от теоретического предела».
- [ ] 8.2.2 График 1: время (или ГБ/с) vs `N` в лог-масштабе, кривые по этапам,
      вертикальные линии на границах L1/L2 — главная иллюстрация отчёта.
- [ ] 8.2.3 График 2: roofline с точками всех этапов.
